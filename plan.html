Keel plan · 6 Nov 2026

Keel

A small TypeScript board the whole team can boot in seconds, run the same way on a laptop and on a server, and watch in two observability accounts: one for the product, one for the machines.

How the pieces work is in the explanation. The phase-by-phase build, with routes, bodies, and a test script per phase, is in the implementation plan.

The product

One repository, named Keel. Keel is a team board: sign in, open a board, create a card, move it, comment, search. Beside it sits Studio, the room where the team rehearses realistic usage against whichever environment they pick.

Keel speaks one telemetry protocol, OTLP, to a collector on the same machine. The collector is the only process that holds a Datadog, Sentry, or OpenObserve credential. It sends what users do to the app account, and it sends the machines to the infra account. Changing vendor, or moving from a laptop to production, changes the collector’s config and the environment name. Keel stays the same.

What “send metrics” means

Studio does not write a number into a vendor. It signs people in and has them use Keel. The API then emits the metric, the log, and the trace. A flat counter with nobody behind it would not look like a person on a chart.

How it fits together

One card, end to end

What the repo has to include

  • A run id on every signal the runner causes, so “it worked” is a search.
  • A debug exporter, so the team can build with zero vendor accounts.
  • Two vendor organizations. A filter inside one account does not keep the product and the machines apart.
  • Keel’s own OpenObserve when that vendor is in use: two organizations, keel-app and keel-infra, on a dedicated endpoint.
  • Ports off the defaults, so Keel can run beside other local tools.
  • Studio on its own origin, so the control room is not product traffic.
  • One journey file that both the computer and the browser can play.
  • A target allowlist, so a production run cannot be aimed at localhost, and a laptop run cannot be aimed at the server.
  • The same Postgres in every environment.

The board

Three roles — owner, member, viewer — make a forbidden action a normal event. A viewer can look and search. A member can create, move, and comment. An owner can move someone else’s card.

Screens

  • Sign in.
  • Launch board: Todo, Doing, Done.
  • Card drawer: title, column, comments.
  • Search.

Seed, fixed ids

Boot seeds one workspace, Northwind, one board, Launch, twelve cards, and three people: Ada (owner), Grace (member), Linus (viewer). Emails are ada@keel.test, grace@keel.test, linus@keel.test. Ids are fixed so a journey can name them. Local seeds on every boot and is idempotent. Production seeds only when KEEL_SEED=1, so a redeploy does not duplicate the board.

The cast logs in. A journey creates a fresh account only when the feature under test is sign-up itself, with an email actor+<runId>@keel.test, and only in local or local-prod. A new user on every run looks like a bot farm and hides the series the team is trying to see.

Local, and the honest clock

The first run on a new laptop pulls Postgres and the collector. That is minutes, once. Every start after that, with images already present and the volume warm, has a budget doctor prints:

  • Web responding in under 3 seconds.
  • API /ready in under 5 seconds.
  • Collector health in under 5 seconds.

Edits to the API reload through tsx watch. Edits to the web and to Studio reload through Vite. Postgres and the collector stay up across reloads. ./scripts/down is the whole stop story.

Local-prod

Compose runs keel-web, keel-api, keel-studio, Postgres, and the collector on one network. Images come from the Dockerfiles. Nothing bind-mounts the source tree. Environment variables come from .env, with KEEL_ENV=local-prod. Healthchecks gate startup order. The collector config is rendered from the same template production uses.

Local-prod matches process boundaries, the built assets, startup order, the health endpoints, and the export path. It is still one machine. It has no second replica and no load balancer.

Use a second pair of vendor accounts for local-prod when the team has them. When they have only one pair, the environment attribute still separates the series, and the README says which choice the team made. Production accounts and laptop accounts stay distinct as soon as a second pair exists, so a laptop soak does not move the production error rate.

Production

One small Linux server runs the same compose file. GitHub Actions is the deploy.

  1. ci.yml on every pull request: pnpm check, image build with no push, collector validate.
  2. deploy.yml on main: build, push to the registry with OIDC, SSH to the server, docker compose pull and up -d, then curl the public /ready.
  3. The workflow records the image tag. workflow_dispatch with an image_tag input redeploys an older tag. That is the rollback.

Secrets live in the GitHub environment production: DEPLOY_HOST, DEPLOY_SSH_KEY, a pinned known_hosts entry, and the vendor keys. The job writes them to a root-only file on the server and does not echo them. API migrations are short forward-only SQL files applied on boot, each one safe to run twice.

After the image is on the host, the new containers should pass /ready within 30 seconds. The pull is the slow part. The app inside the image does not compile on start.

A deploy ends with a Studio smoke only when a person starts it: one actor, one journey, ten minutes maximum, run id printed in the Actions log. The workflow itself only checks /ready. A deploy that generates traffic on its own will disturb whoever is watching the production account.

Two accounts

One account is the product. The other is the machines. A product dashboard then shows requests, errors, and traces. A machine dashboard shows CPU, the database, and the collector. They do not share a login.

There are two slots, app and infra. One environment uses one vendor at a time. An empty slot stays on the collector log. It is not copied into the slot that has a key. Pasting the same key into both slots is refused. The metric names Studio can show live in packages/catalog/metrics.yaml. The API emits a metric only when that file lists it, and each journey names the rows it moves.

Sentry, specifically

Traces and errors over OTLP are the dependable path into Sentry. Metrics over OTLP need a check on the day they are wired. doctor exports one sample of each signal and records which the endpoint accepted. Keel does not invent a stand-in metric to hide a gap. Datadog’s exporter and OpenObserve’s OTLP endpoint take all three.

Vendor switch

KEEL_COLLECTOR_VENDOR is debug, datadog, sentry, or openobserve. scripts/up renders generated/collector.yaml from collector/base.yaml plus one fragment. Generated files stay gitignored. Keys are environment variables: KEEL_VENDOR_APP_API_KEY and KEEL_VENDOR_INFRA_API_KEY, plus an endpoint and a site or org for each. debug prints to the collector log and needs no key. Studio labels that run “not exported”.

OpenObserve is a cloud account. The application account is KEEL_VENDOR_APP_ENDPOINT, KEEL_VENDOR_APP_API_KEY, and KEEL_VENDOR_APP_SITE. Leave the infra triple empty to use that same account, or set it to a different account. The same key in both slots is also allowed. Keel does not run an OpenObserve server.

App metrics worth querying

  • http.server.request.duration histogram, attributes http.route (the template, never the raw id), http.response.status_code, http.request.method.
  • http.server.requests counter, same attributes.
  • keel.card.created, keel.card.moved, keel.comment.created.
  • Error rate is the 5xx slice of the request counter, plus a 403 and 400 slice for the known bad actions.

Studio

Studio is a separate service the team uses to rehearse usage. Its own logs are keel.signal=infra and service.name=keel-studio. The actions it causes on Keel are ordinary Keel requests, so they land in the app account.

What the operator sees

  • Environment: local, local-prod, or production. The list is studio/targets.json, committed, with base URLs and an allowed host per name. Production’s allowed host is the server’s hostname. A URL whose host disagrees with the name is refused before any request.
  • Mode: Computer or Person.
  • Journey, or a mix.
  • Pace profile.
  • Start, pause, stop.
  • A live strip: who is in, which step they are on, the run id, the error count.
  • A proof line: the run id, the account it should have reached, and the vendor query to paste.

Computer

A Node process signs in over HTTP, holds the cookie, and calls the same routes a person would. It is the mode to leave running. It is still a person, on a clock the team can compress. It is not a metric writer.

Each actor has a state: away, arriving, working, leaving. Arrivals are spaced by a Poisson draw from the pace profile, so they clump and gap the way a morning does. A session length is lognormal, median eight minutes on the script clock, with a tail out to about twenty-five. Inside a session a small Markov chain picks the next journey from the role: Linus reads and searches, Grace creates and comments, Ada also moves other people’s cards. Between steps the runner sleeps a think time from that step’s range. A fatigue factor stretches the gaps slightly as the session goes on. About three percent of journeys are abandoned before the last write. About two percent take a known bad path, empty title or a viewer’s move, and those are real 400s and 403s.

The random source is seeded. Studio prints the seed. The same seed and the same pace produce the same sequence of actions. Wall-clock duration still depends on how fast the API answered.

Time scale is part of the profile and is printed in the UI in the same size as the run id. Local’s default scale is 10: one real minute stands for ten script minutes, so an office pattern is visible before a meeting ends. A rehearsal that should match a wall clock uses scale 1. A chart read without the scale will be wrong, so the scale is not a tooltip.

Against production, Computer starts at one actor and ten minutes until the operator raises it, and the raise requires typing the word production. The cap stays at twenty concurrent actors.

Person

Playwright opens the real web UI. One browser context per actor, so cookies never cross. Typing delay is 40–120 ms per character. Clicks go through the labels in the journey. Headless is the default; headed is a checkbox for when someone wants to watch. Think time still applies between steps and is capped so a rehearsal does not sit in silence. On a failed step the runner writes a screenshot under generated/person/<runId>/.

Person mode is how the team proves the button exists. Computer mode never notices a broken label. Person mode is one actor by default, and it is not the overnight job. Both modes read one file. A step that only one mode can run fails pnpm check, except the fault header, which is marked computer-only.

Faults

A toggle in Studio, default off, sends x-keel-fault: once on a single marked route so the API throws once. That moves the 5xx rate on purpose. The known 400 and 403 stay in the journeys and do not need the toggle.

Journeys and the skill

A journey is a YAML file in packages/journeys. It describes one feature twice: the clicks a person makes, and the HTTP calls the computer makes.

id: create-card
title: Create a card on Launch
feature: cards.create
actors: [member, owner]
steps:
  - id: open-board
    ui: { goto: /boards/launch, see: Launch }
    api: { method: GET, path: /boards/launch }
    thinkMs: { min: 600, max: 2500 }
  - id: add-card
    ui:
      click: New card
      fill: { label: Title, text: Check the collector }
      click: Add
      see: Check the collector
    api:
      method: POST
      path: /cards
      body: { boardId: launch, title: Check the collector, column: todo }
    thinkMs: { min: 800, max: 4000 }

The skill

It lives at skills/keel-journey/SKILL.md, and a person can install that same file as a Cursor skill. Its job is narrow:

  1. Read CATALOG.md and the existing YAML so it does not add a second “create card”.
  2. Read the web app for the route and the visible labels. It may only name a button that exists.
  3. Write one journey with both a ui block and an api block, and a thinkMs range a person would actually pause for.
  4. Run pnpm journeys:check. The schema must accept the file. If the local API is up, the api steps run once and must match the status the file expects.
  5. Stop. The person presses Start in Studio. The skill does not target production, does not hold a vendor key, and does not drive the browser itself.

A workflow that lives only in a chat cannot be replayed by the next person, and it cannot be the thing CI runs. The file is the workflow. The runner is the human. The skill is the author.

Proof

A run is finished when the run id is found in the app account and absent from the infra account. Studio turning green only means the runner completed its steps.

  1. 1
    Operator opens Studio, picks local, Computer, create-card, profile demo, and notes the seed.
  2. 2
    Studio starts the runner with a new keel.run_id, aimed only at local.
  3. 3
    The runner signs in as Grace, waits the sampled think time, and POST /cards with the run headers.
  4. 4
    The API writes the card and exports a span, a log, and the histogram points, keel.signal=app, to 127.0.0.1:4418.
  5. 5
    The collector sends app to the app exporter and infra to the infra exporter.
  6. 6
    pnpm prove --run <id> queries the vendor with the collector’s own credentials. It passes only when the app account has the log and the span, and the infra account does not have that log.

With the vendor set to debug, the same steps end in the collector log instead of an account. Studio says “not exported”. That is a complete local loop, and it is the loop to use until the accounts exist. docs/accounts.md is the click-path for creating the two organizations in each vendor and filling the six key lines.

Team rules

  • One person owns the vendor accounts. Keys live in the team password manager and in GitHub environment secrets. They do not go in chat, in a doc, or in git.
  • .env, generated/, and Playwright artifacts are gitignored. env.schema lists every key as public or secret, required or optional. doctor and CI fail if a secret-shaped value shows up in a tracked file.
  • The local seed password is keel-local-only. doctor fails when KEEL_ENV=production still has that password.
  • Studio’s target file is the only place a base URL is allowed to live. Production cannot resolve to a loopback host. Local cannot resolve to the production host.
  • A production run requires the operator to type production, starts at one actor and ten minutes, and stays under the actor cap.
  • Seed users are @keel.test. There is no real personal data to scrub because none is collected.
  • Anyone on the team may run local and local-prod. Merging to main deploys. The README names who is allowed to press merge.
  • ./scripts/down --wipe is the only destructive local command, and it asks.

Day one

This becomes the README, in this order, with nothing else above the first command except the one-paragraph description.

  1. 1
    Install Node 22, pnpm 9, and Docker.
  2. 2
    pnpm install
  3. 3
    ./scripts/init then ./scripts/up
  4. 4
    Open http://127.0.0.1:4100 and sign in as grace@keel.test with the local seed password. The Launch board is there. Create a card. That is the app.
  5. 5
    Open http://127.0.0.1:4102. Leave the vendor on debug. Run profile demo on create-card. The collector log shows a span with the run id. That is the pipe, before any vendor account exists.
  6. 6
    When an account pair exists, fill the six vendor lines in .env, set KEEL_COLLECTOR_VENDOR, restart with ./scripts/up, run the demo again, and pnpm prove --run <id>.
  7. 7
    ./scripts/down at the end of the day.

Troubleshooting is ./scripts/doctor, then ./scripts/status. The README links to docs/architecture.md, docs/accounts.md, and docs/journeys.md and does not repeat them.

Build order

Each milestone is usable by the team before the next one starts. Later milestones assume the earlier “done when” is true. The section-level build of each milestone, including request bodies and the test script that closes the phase, is in the implementation plan.

M1 The board boots

Web, API, Postgres, seed, sign-in, the Launch board, health and ready, init / up / down / doctor, and the README a new teammate can follow. Structured logs on stdout. No collector yet.

Done when a second person, on a clean laptop, reaches the board from the README without asking anyone, inside the warm-start budget on the second run.

M2 The telemetry contract

packages/otel, the attribute list, the run-id headers, the collector in debug, and an in-memory exporter test that a POST /cards produces a span and a histogram point. CI runs this with no vendor and no Docker beyond what the test already fakes. Browser /otel waits until the person-mode milestone. Server signals are enough to prove the two accounts.

Done when doctor shows the two pipelines, and the unit test fails if the route template is replaced by a raw card id.

M3 Two accounts, one vendor

OpenObserve cloud first, one account or two, because it takes all three signals. Datadog next when keys exist. Routing by keel.signal. pnpm prove.

Done when a demo run id is in the app org’s logs and traces and missing from the infra org’s logs, and the request histogram is queryable in the app org.

M4 Studio and the computer

Studio UI, the runner, profiles, the seeded clock, the role mix, abandon and known errors, the live strip, the production typing gate. Journeys shipped here: sign-in, read-board, create-card, forbidden-move.

Done when two runs with the same seed perform the same steps in the same order, the UI shows the time scale without a hover, and a run aimed at local never calls another host.

M5 A person in a browser

Playwright executor for the same YAML. One actor. Headed optional. Screenshot on failure. One journey runs in CI against the local web.

Done when create-card passes headless in CI, and a headed run is watchable from Studio.

M6 The skill

skills/keel-journey writes comment or search, whichever is still missing, and journeys:check gates the file.

Done when someone who did not write the runner can ask the skill for a journey and then play it in both modes.

M7 Local-prod

Dockerfiles, compose, no source mounts, the shared collector template, a measured cold and warm start written into the README.

Done when a card created against the image shows the same run-id proof as local, and editing a source file does nothing until KEEL_REBUILD=1.

M8 Production

Container registry, deploy.yml, SSH with pinned host key, smoke on /ready, rollback by tag, production keys in the GitHub environment, Studio allowlist pointed at the server.

Done when a merge to main replaces the containers, /ready passes, and a tagged redeploy of the previous sha brings the old image back.

M9 The other vendors

Datadog and Sentry fragments, if OpenObserve was first. No application change. doctor records, per vendor, which of the three signals the endpoint accepted.

Done when changing KEEL_COLLECTOR_VENDOR and restarting is the entire switch, and any Sentry gap is a line in doctor rather than a surprise on a dashboard.

Left out on purpose

  • Kubernetes, Helm, and Terraform. Production is one server and the same compose file as local-prod.
  • A button that posts a raw number to a vendor.
  • Public sign-up, OAuth, email delivery, and mobile.
  • More than one replica. Concurrency comes from actors, not from copies of the API.
  • Sharing Postgres, the collector ports, or OpenObserve with any other project on the laptop.

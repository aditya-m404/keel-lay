Keel

A team board, a way to rehearse a day of use, and a path from that use into observability accounts.

The build steps are in the plan. The phase-by-phase implementation is in the implementation plan.

1. Core idea

Keel is a board for one small team. People sign in, open Launch, and move work across Todo, Doing, and Done. They create cards, comment, and search. Ada owns the board and can move anyone’s card. Grace is a member and does the work. Linus can look and search, and the board refuses him when he tries to change it.

The same board runs in three places. On a laptop it reloads as someone edits. On that laptop again it can run as a built copy of production. After a merge it runs on a server. A person who learned the board in one place can use it in the others.

Studio is the admin panel beside the board. It rehearses a day when the office is empty: a few people arrive, work, pause, and leave. One rehearsal calls the board over HTTP on a human clock. The other opens the real board in a browser and clicks. Both are still using Keel. Signing in and moving a card is the action.

A morning on the board

Grace opens Keel and signs in. The board she lands on is Launch, already holding the cards the team left yesterday. She adds one, “Check the collector”, in Todo. She drags it to Doing when she starts, and to Done when she finishes. She leaves a comment so Ada can see what she found. Linus, signed in as a viewer, can read that comment and can search for the card. When he tries to move it, Keel answers no. The card stays where Grace put it.

That is the product. The roles exist so the board can agree and refuse the way a real team does. The three columns exist so a card has a life, not a single save button. Search exists so yesterday’s card can be found.

The same board in three places

While someone is changing Keel, they run it on their laptop and see the edit as they save. When they want to know the built copy behaves, they start that copy on the same laptop: no live reload, the files inside the image. When the team merges, that same copy is what the server runs. A person rehearsing against the laptop is not writing cards onto the server, and a rehearsal against the server is not writing cards onto the laptop. Studio asks which of the three it is aiming at before it starts, and it keeps that choice for the whole run.

Use of the board leaves a record: how often people act, how long the board takes to answer, which actions were refused, and the line and the path of each request. The rest of this page is how that record is made, how it reaches Datadog, Sentry, or OpenObserve, and how Studio causes a day of use when nobody is sitting at the board.

2. Architecture

Two paths reach the API. A person uses the board. Studio’s runner uses the same API. Both paths write to Postgres and export telemetry to the collector.

A person and a rehearsal are two callers of one API. The browser draws the board and sends the person’s clicks to the API. The runner, started by Studio, sends the same kinds of requests, with a cookie it earned by signing in. The API does not care which caller it was. It checks the session, checks the role, writes Postgres, and records what happened. Postgres is the board. The collector is not on that path. A card is saved even when no vendor is configured.

The record is a second path, beside the save. After the API has written the card, it hands three things to a small library in the same process: a metric update, a log line, and a trace span. That library speaks only to the collector. The collector later decides which account, if any, receives them. Studio’s own screens are not part of the board’s record. They are marked as the machines, so a chart of “cards created” does not count someone opening the admin panel.

Keel web

The web is the board a person sees: sign in, Launch, the card drawer, search. It holds no vendor key and no database password. A click becomes a request to the API, and the API’s answer is what the page draws. When the page itself has something to report, such as how long the board took to appear, it posts that to the API’s /otel path. The API forwards those bytes to the collector and does not inspect them for a key. The browser never learns which vendor is in use.

Keel API

Every board action arrives here. The API reads the session cookie, loads the person, and applies the role. A viewer’s move is refused before any write. A member’s create is written, then recorded. The recording is three updates in the same request: add one to the request counter, record how many milliseconds the handler took, and add one to the business counter for that action, such as cards created. Beside those numbers it writes one log line and closes one trace span. The route on the metric is the template, /cards, never the id of the card that was just created, so a chart stays a chart of the feature rather than a chart of every card.

Postgres

Users, sessions, the Launch board, cards, and comments live here. The laptop, the built copy, and the server each have their own database, so a rehearsal in one place cannot edit the board in another. The schema is the same in all three, which is why a journey written against the laptop still makes sense against the server.

Collector

The collector is a separate process. It listens for OTLP, batches what arrives, and reads keel.signal on each item. app goes to the product account’s exporter. infra goes to the machine account’s exporter. If that exporter has no key, the batch is printed to the collector’s own log and is not sent anywhere else.

The two accounts

The app account is where a person looks for the board: request rate, latency, refusals, cards created, moved, and commented, plus the log line and the trace of each of those actions. The infra account is where a person looks for the machines: CPU, memory, Postgres, the collector’s queue, and Studio’s own process. They are separate logins so a product chart is not mixed with a host chart.

Studio and the runner

Studio is the screen where an operator chooses the environment, the ingestion type, the journey, and the pace, then presses start. The runner is the process that then acts. It signs in as Ada, Grace, or Linus and calls the API. The API does the recording. The runner’s job ends at the request.

One card, from the click to the account

Take Grace creating “Check the collector” during a rehearsal whose id is run_01H.

  1. 1
    The runner, or Grace’s browser, sends POST /cards with her session cookie and the headers x-keel-run-id, x-keel-actor: grace, x-keel-journey: create-card, and x-keel-step: add-card. A person at the keyboard during ordinary use sends no run headers. The card is still saved. It simply has no rehearsal id.
  2. 2
    The API checks that Grace is a member. It inserts the card in Todo on Launch. Postgres now has the row. This has already succeeded before any vendor is involved.
  3. 3
    Still inside that request, the API records the duration of POST /cards, adds one to the request counter with status 201, and adds one to keel.card.created. It writes a log line naming Grace, the card, and run_01H. It closes a span for that request with the same ids. All three are marked keel.signal=app.
  4. 4
    The library in the API batches this with the other points from the last second or two and posts them to the collector. The collector’s app exporter, if it has a key, writes the numbers to the account’s metric store, the line to its log store, and the span to its trace store. Someone searching that account for run_01H finds all three together.

The counters worth naming are http.server.requests, the histogram http.server.request.duration, and the business counters keel.card.created, keel.card.moved, and keel.comment.created. Error rate is not a separate feed. It is the 5xx slice of the request counter, plus the 400 and 403 answers the board returns on purpose, such as an empty title or Linus trying to move a card. Host CPU is not in this list. It is scraped on the machine path and never carries run_01H.

The same boxes, three ways of starting

What stays the same is the board, the API, the journey files, and the shape of the collector. What changes is where the process runs and which account pair the collector is allowed to use. On the laptop, saving a source file reloads the API, so the next card uses the new code. On the built copy, saving a source file does nothing until the image is rebuilt. On the server, a merge replaces the running image, and the previous image tag is how the team puts the old copy back. Each of the three tags its signals with its own environment name. A chart of cards created can be split by that name, which is how a laptop rehearsal is kept out of the production line even when, early on, both environments temporarily share one account pair.

From OTLP to the vendor

Keel never calls Datadog, Sentry, or OpenObserve. The web and the API speak OTLP to the collector on the same machine. OTLP is a single export format with three payloads in it: metrics, logs, and traces. The collector is the only process that holds a vendor key, and it is the process that turns those payloads into the vendor’s own stores.

What leaves the API

The library inside the API does not send on every request. It holds a small batch and flushes on a short timer, or sooner if the batch fills. The flush is an HTTP post to the collector. One post can carry metric points, log records, and spans together. Each item already has its attributes: service name keel-api, the environment, keel.signal=app, and the run id when a rehearsal caused it. The cookie and the authorization header are stripped before this post is built. A vendor never sees a session.

What the collector does with the post

  1. 1
    The receiver accepts the post and decodes the three payloads. A failure to decode is the collector’s own error. The card in Postgres is already saved.
  2. 2
    A batch processor groups items for a moment so the vendor is called in handfuls, not once per card.
  3. 3
    A router reads keel.signal. Items marked app are copied to the app pipeline. Items marked infra are copied to the infra pipeline. An item with no mark is dropped and counted, so a missing label cannot fall into an account by accident.
  4. 4
    Each pipeline ends in one exporter. The exporter is the translation. Metrics stay metrics and are written to the vendor’s metric store. Log records stay logs and are written to the log store. Spans stay traces and are written to the trace store. The run id is an attribute on all three, which is why one search finds the card’s number, its line, and its span.

Take the log line for Grace’s card. In the API it is a record with a timestamp, the message, and the attributes above. The collector does not rewrite the message into a metric. The app exporter sends that record to the vendor’s log intake. In Datadog that intake is the exporter’s log endpoint, using the app account’s API key and site. In OpenObserve it is an OTLP HTTP post to the application account’s organization. The infra pipeline uses that same account when its own endpoint is empty, and a different account when the infra endpoint is set. In Sentry it is an OTLP HTTP post to that Sentry organization. The same split happens, in the same flush, for the histogram point and the span. They do not wait for each other beyond the batch, and they do not land in each other’s stores unless the two slots were pointed at one account on purpose.

If the vendor answers 401, the exporter stops sending and the collector log says the key was refused. Points already saved in Postgres remain. Points not yet accepted by the vendor sit in the batch until the retry budget ends, then they are dropped and counted. Keel does not keep a second copy to replay later. If the vendor is down, the board keeps taking cards. The record for those seconds is the gap in the account, visible because the request counter on the board’s side and the series in the account stop matching.

VendorHow the collector hands off
DatadogThe Datadog exporter. One API key per account. Site is part of the account, such as the regional endpoint.
OpenObserveOTLP HTTP to the account’s endpoint. The key is the full Basic header value. Infra can be the same account or a different one.
SentryOTLP HTTP to that Sentry organization. Traces and logs are the dependable delivery. If the metrics endpoint refuses the sample, doctor says so. The metric is not copied into another account to hide the gap.

One environment uses one vendor at a time. Choosing Datadog means both slots export to Datadog. Switching to OpenObserve is a config change and a restart, and Keel itself does not change. Local, local-prod, and production may each point at their own pair, so a laptop rehearsal does not write into the production accounts.

How many accounts, and one account alone

There are two slots, not a growing list: app and infra. A third destination would be a new pipeline, and this version does not have one. One environment uses one vendor at a time, so both slots of that environment speak Datadog, or both speak OpenObserve, or both speak Sentry. Local, local-prod, and production may each have their own pair. That is at most six organizations. A rehearsal aimed at the laptop uses the laptop’s pair. It does not write into the server’s pair.

Filling a slot means giving that pipeline a key and an endpoint. Leaving it blank means that pipeline prints to the collector log. The other pipeline is not a backup for it.

What is filled inWhat happens
Neither slotBoth pipelines print locally. Studio marks the run “not exported”. The board still works.
App onlyProduct metrics, logs, and traces leave for the app account. Machine signals stay on the collector log. They are not folded into the app account.
Infra onlyHost, database, collector, and Studio’s own process leave for the infra account. A card’s log and its request metrics stay local.
Both, different organizationsThe split the diagrams show. A run id is found in the app account and is absent from the infra account.
Both slots, the same keydoctor refuses to export. Pasting one key twice would put the product and the machines in one login. Leave the unused slot empty instead.

An empty slot is a visible gap, not a fallback. The filled account receives only the pipeline aimed at it.

Suppose only the app key is set, and Grace’s rehearsal creates a card while the laptop’s CPU is busy. The card’s counter, log, and span arrive in the app account, searchable by the run id. The CPU sample is printed in the collector log and is absent from the app account. The reverse, only the infra key, puts the CPU sample in the infra account and leaves the card’s log on the collector. Someone looking at the one account they configured will not see the other half, and Studio’s catalog marks that half “not exported”.

Pasting the app key into the infra slot as well is refused before export starts. One login would mix the card counter and the CPU sample, which is the split the two slots exist to prevent. Debug mode ignores keys entirely and prints both pipelines. It is how the team runs before any account exists.

3. Admin panel

Studio is a separate app on its own address. An operator uses it to aim a rehearsal at one environment and to watch the metric catalog. Opening Studio does not create a card and does not move a product metric. Studio’s own requests are marked keel.signal=infra, so they belong with the machines. The rehearsal it starts is different: those calls are ordinary Keel requests, and the API records them as the product.

What happens when the operator presses start

  1. 1
    Studio checks the chosen environment against the allowed host. Local must be the laptop. Production must be the server. A mismatch stops here, before any request.
  2. 2
    It mints a run id and shows it. Every request of this run will carry that id. It also shows the time scale, so a compressed rehearsal is not read as wall-clock traffic.
  3. 3
    It starts one runner and hands it the target address, the ingestion type, the journey, the pace, and a seed. The runner cannot change the address afterward.
  4. 4
    The runner acts, by the rules of the type below. The API writes the board and records the metrics. Studio’s live strip reads the runner’s progress: who is signed in, which step they are on, how many refusals.
  5. 5
    When the run ends, Studio looks up the run id in the account named on each catalog row the journey claimed. A row is found or missing. Pause freezes the runner’s clock. Stop ends the session cookies. Neither pause nor stop deletes the cards already written.
PieceWhat it does
Studio screenStart, pause, and stop. Shows who is active, which step they are on, the run id, the error count, and the time scale. Also shows the metric catalog and whether each row’s account is configured.

How Studio knows which metrics exist

Studio does not ask the vendor “what metrics do you have?”. The vendor only knows what has already arrived, so a metric nobody has moved yet would be invisible, and a metric from some other system would show up as if it were Keel’s. The list is a file in the repo, packages/catalog/metrics.yaml, and Studio reads that file when it starts.

A row says the name, the kind (a counter or a histogram), the unit, the account slot, and what moves it. Product rows name the journeys that move them. Machine rows say always, because the collector scrapes them whenever the stack is up. The API is allowed to emit a name only when the file has that row. Studio is allowed to show a name only when the file has that row. A check fails if the API and the file disagree, so the screen cannot list a metric the board will never send, and the board cannot send a metric the screen has never heard of.

name: keel.card.created
kind: counter
unit: "1"
slot: app
moved_by: [create-card]
---
name: process.cpu.utilization
kind: gauge
unit: "1"
slot: infra
moved_by: [always]

On the catalog screen each row shows three facts Studio can know without guessing: the slot, whether that slot currently has a key, and, after a run, whether the run id was found in that account. Health rows have no run id. Their status is whether fresh samples are arriving, which Studio reads from the collector, not from a rehearsal.

A journey file names the rows it promises to move. create-card lists keel.card.created, the request counter, and the duration histogram. Studio uses that list twice. Before the run it tells the operator what should move. After the run it checks those rows and no others. A comment counter staying still during a create-card run is expected, not a failure.

The four ingestion types

An ingestion type is who acts, and on what clock. It is not a different pipe. Computer, Person, and Machine all end in the same API, and the API records metrics the same way. Health never calls the API. The table is the index. The sections after it are the mechanism.

Computer

Computer is the rehearsal to leave running. A Node process signs in over HTTP and uses the board. Nobody watches a browser. The timing is still a person’s timing, drawn from a clock the operator can compress.

  1. 1
    The runner builds the cast from the pace. Office uses three: Ada, Grace, and Linus. Each has a role, so the runner will not ask Linus to create a card unless the journey is the forbidden one.
  2. 2
    Arrivals are not a timer of one second. The gap until the next person appears is drawn from a Poisson distribution around the pace’s mean, so people clump, then the board goes quiet. A session length is drawn from a lognormal curve, most of them around eight minutes on the script clock, a few much longer.
  3. 3
    On arrival the actor sends POST /session with that person’s email and the seed password. The API returns a cookie. The runner keeps that cookie for this actor only. Ada’s cookie is never sent as Grace.
  4. 4
    While the actor is working, the runner picks a journey by a small set of weights. A viewer mostly reads and searches. A member creates, moves, and comments. An owner may also move someone else’s card. About three percent of journeys are abandoned before the last write: the actor simply leaves. About two percent are the known bad journeys, an empty title or a viewer’s move, so the board returns a real 400 or 403 and the error slice of the request counter moves.
  5. 5
    Each step sleeps for a think time drawn from the range in the journey, stretched a little as the session goes on, then sends the HTTP call with the run headers. The API writes the card and records the metric. The runner does not increment anything itself.
  6. 6
    When the session length is used up, the actor calls DELETE /session and returns to away. The next arrival is another draw.

The random draws come from a seed Studio prints. The same seed and the same pace produce the same sequence of sign-ins and journeys. The wall clock still depends on how fast the API answered. The default scale on the laptop is 10: one real minute stands for ten minutes of the script, so an office pattern is visible in a sitting. Scale 1 means the pauses are the real pauses. The scale is on the screen next to the run id.

Against production, Computer starts at one actor and ten minutes. Raising that requires the operator to type the word production. The cap is twenty actors. The flat Machine type is a different choice, described below. It is not what Computer becomes when the pace is tight.

Person

Person plays the same journey file in a real browser. It exists because Computer never looks at the page. A renamed button, a broken form, or a card that never appears still looks like a successful HTTP call to Computer, and like a failure to a person.

  1. 1
    Studio starts the runner in person mode with one actor. A browser context is created for that actor alone, so a second person, if the operator adds one later, does not share the cookie.
  2. 2
    The runner reads the ui half of each step. goto: /boards/launch opens that URL on the environment’s web address. see: Launch waits until that text is on the page. If it never appears, the step fails and a screenshot is written under generated/person/<runId>/.
  3. 3
    A click finds the button by its visible label, the same words a person reads. Typing goes into the field with that label, at 40 to 120 milliseconds a character, so the keystrokes are not a single paste. The think time from the step still applies between actions, and it is capped so a demo does not sit for minutes.
  4. 4
    The page then calls the API the way it always does. The runner has attached the run headers to that browser. The API writes the card and records keel.card.created, the request counter, and the duration, exactly as it does for Computer. Person mode does not have its own metric names.
  5. 5
    Headless is the default. Headed is a checkbox when someone wants to watch the cursor. One actor is the default because a browser is heavy and because the point is to see the feature, not to imitate a crowd. The crowd is Computer’s job.

If a step has a ui block and no api block, or the other way around, the check fails before a run. The two halves are the same feature. The fault header that asks the API to throw once is the exception, and it is marked computer-only, because a person in the browser cannot send it.

Machine

Machine is a steady rate through the real API. It is opt-in, and it is labeled so it can be kept off the human charts. It exists so a load check is not hidden inside the office pace by shortening the pauses until they stop looking human.

  1. 1
    The operator picks Machine and a rate. The default is five requests a second. The runner will not go past twenty in flight.
  2. 2
    It signs in once per actor it is allowed, then repeats the journey’s HTTP steps on a fixed interval. There is no Poisson arrival, no long session tail, and no fatigue. The gaps are even.
  3. 3
    Every request is still a real Keel call. An empty title, if that journey is included, is still a real 400. The API still adds to the same counters. The runner sets keel.pace=machine on the headers so a chart of human use can exclude the series.
  4. 4
    Stop ends the loop. Cards created during the rate remain on the board. The catalog check is the same as Computer: the rows the journey named should show the run id in the app account, when that slot has a key.

Health

Health is the ingestion that has no start button. It is the machines reporting themselves for as long as the stack is up, whether or not anyone is rehearsing.

  1. 1
    The collector, on its own timer of about fifteen seconds, reads host CPU and memory, asks Postgres for connections and database size, and reads its own queue depth. These scrapes do not pass through the Keel API and do not create cards.
  2. 2
    Each sample is marked keel.signal=infra and has no run id, because no rehearsal caused it. The environment name is still set, so the laptop’s CPU and the server’s CPU stay apart.
  3. 3
    The infra pipeline exports them when that slot has a key. When it does not, they print in the collector log. They are never attached to the app pipeline to fill a gap.
  4. 4
    Studio lists these catalog rows as always on. The status is whether samples newer than the scrape interval are present. A rehearsal can be running at the same time. The two do not share a clock, a run id, or an account.

Across all four types, the rule is the same. Product numbers change because the API handled a real call. Machine numbers change because the collector looked at the host. Studio’s job is to choose the caller and the clock, then to say whether the account the catalog named actually received the run.

Keel is the board. Studio rehearses a day of using it. The catalog is the list of metrics that exist, and each ingestion type is a way those metrics move. The collector carries them to the account slot that is actually filled in.
